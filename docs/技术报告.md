# MiMo-Lite 自研大模型技术报告

**项目**：在单台消费级笔记本（RTX 5070 Laptop，8GB 显存）上从零预训练一个大语言模型
**架构对标**：小米自研 MiMo 系列
**作者**：Jerry ｜ 实施：Mavis 协助

---

## 摘要

本项目在**零云端算力、零预训练权重**的条件下，完整走通了
「语料 → tokenizer → 预训练 → SFT → 强化学习 → GGUF 导出 → llama.cpp 本地推理」
的全链路，产出一个 1.08 亿参数的自研基座模型 **MiMo-Lite**。

核心结论：

1. **方法论可以缩放，参数规模不能**。小米 MiMo-V2.5-Pro 是 1.02 万亿参数 / 27 万亿 token
   预训练，本机是 0.108 亿参数 / 计划 2 亿 token，差 5~6 个数量级。
   但 MiMo 的三个招牌设计——混合注意力、MTP、多阶段后训练——都能在笔记本上复现。
2. **8GB 显存足以跑通全链路**。实测训练吞吐 1.41 万 token/s，显存峰值 3.7GB。
3. **工程细节决定成败**。本项目记录了 7 个会导致"静默错误"的坑，其中 RoPE 风格不匹配
   和注意力因果性泄漏两个如果不提前发现，会浪费数小时训练后才发现模型完全不可用。

## 一、与小米 MiMo 的技术对标

### 1.1 MiMo 的公开技术要点

根据小米官方技术报告（MiMo-V2-Flash / MiMo-V2-Pro / MiMo-7B）：

| 技术 | 官方描述 |
|---|---|
| 稀疏 MoE | V2-Flash：309B 总参 / 15B 激活；V2-Pro：1.02T 总参 / 42B 激活 |
| 混合注意力 | 滑动窗口注意力(SWA) 与全局注意力(GA) 按 **5:1** 交错，窗口 128 token；V2-Pro 提升到 7:1 |
| KV Cache 优化 | 固定大小 KV Cache，长上下文下存储降低约 7 倍 |
| MTP | 3 层多 token 预测模块，推理时作 draft 模型，投机解码提速 2.6~3.6 倍 |
| 数据 | V2-Flash 预训练 27 万亿 token，FP8 混合精度，原生 32K 上下文 |
| 后训练 | 三阶段：SFT → 领域专精 RL → **多教师在线策略蒸馏 MOPD** |
| 投机解码 | 复用 MTP 作为原生草稿模型，实现 token 级并行 |

### 1.2 本项目的取舍

| MiMo 原做法 | MiMo-Lite 落地 | 差异原因 |
|---|---|---|
| 稀疏 MoE 309B/1.02T | Dense 108M | MoE 需要 expert 并行与容量因子调优，单卡无法有效利用；dense 反而能榨干显存 |
| SWA:GA = 5:1，窗口 128 | 12 层 SWA + 2 层 GA，窗口 128 → 实际 **6:1** | 14 不是 6 的倍数，只能落在第 5、11 层。**未完全复刻**，比例待消融 A-003 定夺 |
| 3 层 MTP | 1 层 MTP（预测 t+2） | 108M 模型上多层 MTP 收益有限且吃显存 |
| 27 万亿 token | 计划 2 亿 token | 受吞吐与时间约束，约 0.7% |
| 自研 tokenizer | 自训 byte-level BPE 16K | 无差异 |
| SFT → 领域 RL → MOPD | SFT → GRPO（可验证奖励） | MOPD 需要多个领域 teacher，单卡只能做单 teacher 简化版 |
| FP8 混合精度 | bf16 autocast | 5070 Laptop 不支持 FP8 训练路径 |

### 1.3 KV Cache 的实际收益

MiMo 用 SWA 的核心动机是 KV Cache 恒定。本项目额外叠加 GQA：

```
多头注意力基线 : 12 头 × 64 维 = 每 token 768 维 KV
GQA 后         : 4 KV头 × 64 维 = 每 token 256 维 KV   → 3× 压缩
SWA(128 窗口)  : KV 长度上限 128，与序列长度无关        → 长文本下再大幅压缩
```

在 ctx=2048 时，相对"12 头 + 全局注意力"基线，KV Cache 理论占用约为
`256 × 128 / (768 × 2048) ≈ 2%`。

## 二、模型规格

```
参数量        108,160,896 (108.16M)
词表          16,384（自训 byte-level BPE，中文 1.85 字/token）
层数          14
隐藏维度      768（12 头 × 64 维）
FFN           SwiGLU，中间层 2048
注意力类型    第 0-4,6-10,12-13 层 SWA(128)；第 5,11 层 GA
KV 头         4（GQA）
归一化        RMSNorm + QK-Norm
位置编码     RoPE（interleaved/NORM 风格，theta=100000）
权重共享      embedding 与 lm_head tying
MTP 模块      1 层，预测 t+2，仅训练时提供辅助损失
```

参数量分布：

| 组件 | 参数量 | 占比 |
|---|---:|---:|
| token embedding（与输出共享） | 12,582,912 | 11.6% |
| 14 层 Transformer | 94,289,408 | 87.2% |
| MTP 模块 | 1,288,576 | 1.2% |

> **更正：SWA:GA 实际是 6:1，不是 5:1。**
> `ga_interval=6` 配 `n_layer=14` 只能落在第 5、11 两层（14 不是 6 的倍数），
> 所以真实比例是 12 SWA : 2 GA = **6:1**，而不是设计稿里写的 5:1。
> 精确的 5:1 需要 `n_layer ∈ {12, 18, 24}`。
> 连带影响：当前基线只有 **2/14 = 14%** 的层具备长程检索能力，
> 这个比例是否最优尚未验证 —— 见消融 A-003。

### 4.4 训练/验证集隔离

消融的前提是 val loss 可信，否则所有架构/优化器对比都是噪声。

- 每个数据流**尾部 2%** 划为验证集，训练只在前 98% 里取块，位置零重叠
  （zh 7,328,870 / en 5,538,300 token）。
- 验证批次**按 batch size 缓存后固定复用**。这里修掉一个隐蔽缺陷：
  原本每次 eval 都从同一个固定种子 rng 继续取样，rng 会随 eval 次数推进，
  于是每次验证看到的其实是不同数据 —— 波动会掩盖真实差异，跨 run 也无法比较。
- 中英混合用**最大余数法**精确分配（原先 `int(bs*ratio)` 截断会让实际比例漂移，
  且 `micro_bs` 小时会给次要语种分配 0 条并直接崩溃）。

### 4.5 新增的调度与优化器开关

| 开关 | 命令行 | 出处 |
|---|---|---|
| WSD 调度 | `--sched wsd --wsd-decay-ratio 0.2` | MiniCPM, arXiv:2404.06395 |
| GradPower | `--gradpower-p 1.2` | ICML 2026, arXiv:2505.24275 |
| 关闭梯度检查点 | `--no-grad-ckpt` | **实测反而更慢**，见 4.3；仅在撞 OOM 时用 |
| 显式 GA 层 | `--ga-layers 6,7` | 消融 A-003 |
| FlexAttention | `--attn-impl flex` | block-sparse SWA |

**GradPower**：对梯度做逐元素 sign-power 变换 `φ_p(g) = sign(g)·|g|^p`
再交给原优化器，不动动量、二阶矩与超参。`p = 1.2` 是论文在 LLaMA-0.2B/C4 上
一次定下、随后 66M→2B / dense→MoE / C4+OpenWebText / cosine+WSD 全程沿用的默认值。
作用在**累积后、裁剪前**的梯度上。论文报告 LLaMA 终局 loss 改善约 0.02–0.03 nats，
且**最大增益恰好出现在 WSD 调度下** —— 这正是消融 A-005 采用 2×2 全因子设计的原因。

**FlexAttention 的诚实预期值**：seq=512 / window=128 时，滑窗矩阵只占稠密矩阵的
21.9%，理论上可跳过约 78% 的注意力 FLOPs；但注意力只占整层 FLOPs 的约 33%，
且其中只有二次项可稀疏。**净收益约 5%**，不是我最初估计的 1.5–2×。
本机 CUDA 路径当前因缺 `triton` 不可用，代码已实现并会在运行时自动降级到稠密 mask
（不静默出错）。优先级低于关闭梯度检查点 —— 但后者的收益经实测为**负**，见 4.3。

### 4.3.1 梯度检查点：实测推翻了先前的判断

我此前判断「关闭梯度检查点可省约 25% 计算」。**方向是错的。**
在预训练跑完后做了唯一变量为梯度检查点的受控对比：

| micro_bs | accum | 梯度检查点 | 吞吐 | 显存峰值 | step 耗时 |
|---:|---:|:---:|---:|---:|---:|
| 8 | 4 | **开** | **16.6 k token/s** | 3.73 GB | 992 ms |
| 8 | 4 | 关 | 11.3 k token/s | 6.50 GB | 1450 ms |
| 16 | 4 | 开 | 11.8 k token/s | 5.42 GB | 2775 ms |

关闭后吞吐**掉了 32%**，显存反而从 3.73GB 涨到 6.50GB（1.74 倍）。

原因：108M 规模下激活显存本来就不是瓶颈（开检查点时也只用掉 8GB 中的 3.73GB）。
梯度检查点的代价是一次完整前向重算，而它换来的收益在这里体现为更好的
访存局部性 —— 这部分收益大于重算开销，所以净效果是**开着更快**。
这个结论对「小模型 + 单卡 + 显存有富余」这一类场景普遍成立，不能照搬
大模型「显存紧张所以必须开检查点」的直觉。

**结论**：默认保持开启；`--no-grad-ckpt` 仅在更大 micro_bs 撞 OOM 时才用。

## 四点五、消融实验框架（`ablate.py`）

单卡 8GB 下，**同样 GPU 小时，用来产出「结论」的信息密度远高于产出权重**。
`ablate.py` 把一组配置逐个跑完，收集固定验证集上的终局 loss，自动出对比表。

三条不可妥协的实验纪律：

1. **等参数量** —— 跨架构比较必须配平，否则区分不出「深更好」还是「大更好」。
2. **等 token 预算** —— 所有配置用同样的 steps × seq_len × batch。
3. **同验证集** —— 见 4.4，验证批次固定复用。

每个配置跑在**独立子进程**里：某个配置 OOM 或崩溃不会带走整轮消融。

| 套件 | 回答的问题 | 设计 |
|---|---|---|
| **A-003** | SWA/GA 比例与**位置**是否应当均匀交错？ | 固定 14 层 × 768，参数量天然 100% 相同。比例段扫 13:1 / 6:1 / 2.5:1；位置段固定 2 个 GA 层（比例恒为 6:1），比底层 / 交错 / 连续中段 / 顶层四种排布 |
| **A-001** | 等参数下深度与宽度哪个更划算？ | 20 层 / 14 层 / 8 层，自动配平 d_model |
| **A-005** | WSD 与 GradPower 各自的主效应与交互？ | 2×2 全因子：{cosine, WSD} × {AdamW, AdamWPower} |

**A-003 为什么固定 14 层**：换成 12 层就必须重新配平 d_model 才能等参数，
而宽度一动，RoPE 维度、注意力头数、GQA 组大小全都跟着动 —— 那就不是在测
「SWA 比例」了。**保持 14 层不变，参数量天然相同，val loss 的任何差异都只能
归因于 GA 层的位置。** 这是整个框架里最干净的一处设计。

**配平求解器的两个坑**（都已修）：

- 解析式参数量公式曾与 `model.py` 漂移，算出 98.13M 而真实是 108.16M（差 9%）。
  现改为用 `meta` device 实例化**真实模型**数参数，不分配内存且瞬时完成。
  参数量配平是所有跨架构结论的前提，这种量级的偏差会直接毁掉消融结论。
- `n_head` 为素数（如 13）时，凑不出 GQA 组≈3，相邻网格点之间参数量跳变 28M。
  现限制 GQA 组大小落在 [2,4]，把这类配置排除。

**调研给出的方向（与当前实现相反）**：ConSA（arXiv:2606.18056，0.6B/1.7B）
学到的分配是「SWA 在底层、FA 集中于**连续**中间层块」，明确偏离均匀交错；
BOSCH（arXiv:2604.05942，ACL 2026）发现逐层自适应 SWA 比例优于层间启发式。
两者独立指向同一结论 —— 这就是 A-003 被列为投入产出比最高消融的原因。

## 五、后训练

### 5.1 SFT 阶段

对话模板：
```
<|bos|>用户：{内容}<|sep|>助手：{回复}<|eos|>
```
损失仅在"助手回复 + `<eos|>`"上计算，prompt 段全部置 -100。

数据构成（102,054 条）：

| 来源 | 条数 | 用途 |
|---|---:|---|
| silk-road/alpaca-data-gpt4-chinese | 52,049 | 中文通用指令 |
| open-thoughts/OpenThoughts-114k | 30,000 | 长链思维链 |
| AI-MO/NuminaMath-CoT | 20,000 | 数学推理 |
| Jerry 自建语料 | 5 | 中英翻译（`F:\AI\datasets\my_corpus`） |

冒烟验证：246/300 样本可用，验证 loss 8.36 → 7.89。

### 5.2 GRPO 阶段

对标 MiMo-7B 的"13 万道可验证数学题做 RL"。

**为什么用 GRPO 而不是 PPO**：GRPO 对同一道题采样 G 条回答，用组内奖励的均值/标准差
作为 baseline 计算 advantage，省掉一个同等大小的 critic 网络。在 8GB 显存上，
多一个 108M 的 critic 就意味着要么缩小 batch、要么开梯度检查点、要么上 CPU offload。

奖励设计（纯可验证，不依赖奖励模型）：

| 情形 | 奖励 |
|---|---:|
| 答案正确 + 有 `<answer>` 标签 | +1.2 |
| 答案正确 + 无标签 | +1.0 |
| 答案错误 + 有标签 | +0.2 |
| 有数字但无法抽取 | 0.0 |
| 完全没给答案 | −0.5 |
| 输出超长 | −0.1 |

答案抽取的兜底策略值得强调：优先 `<answer>` 标签，失败则取**全文最后出现的数字**。
若不做兜底，RL 早期模型还没学会输出标签，会被大面积判负导致无学习信号。

单元测试覆盖 8 个奖励用例 + 3 个抽取用例 + 5 个归一化用例，全部通过。

## 六、部署

### 6.1 GGUF 导出

MiMo-Lite 的骨干与 Qwen3 完全同构（RMSNorm + RoPE + SwiGLU + QK-Norm + 无 bias + GQA），
因此以 `qwen3` 架构导出 GGUF —— 这是 llama.cpp 支持最完整、且原生支持滑动窗口注意力的架构。

导出时排除 MTP 张量（llama.cpp 不认识），共写出 **157 个张量**。

### 6.2 llama.cpp 实测

用随机初始化权重（未训练）验证链路，模型正常加载并生成，中英文 token 往返无损：

```
build      : b10919-d3146f2b5
model      : out/mimolite-test.gguf
ftype      : F16
modalities : text
[ Prompt: 340.1 t/s | Generation: 403.3 t/s ]
```

### 6.3 导出保真度检验

模型训练到 step 500（验证 loss 9.85 → 6.62）后，系统性检验导出链路。

**问题一（已修复）：预分词器不一致**

用 `llama-tokenize` 对同一段 1500 字中文文本分别分词，发现：

| | token 数 | 前 12 个 id |
|---|---:|---|
| PyTorch（HF tokenizers） | 1104 | `4857, 277, 21, 5591, 2368, 951, ...` |
| llama.cpp（修复前） | 1110 | `1018, 22, 277, 21, 5591, 2368, ...` |
| llama.cpp（修复后） | 1104 | `4857, 277, 21, 5591, 2368, 951, ...` |

根因：GGUF 里的 `tokenizer.ggml.pre` 被写成 `"default"`，而本项目用的是
HF ByteLevel（GPT-2 同款正则），必须写 `"gpt-2"`。写成 default 时 llama.cpp
在词首/空白处的切分与训练时不一致，导致整段文本的 token 序列都错位。

修复后**逐 token 完全一致**。

**问题二（已定位并结论化）：0.22 nats 困惑度差距 —— 不是 bug，是测量方式错误**

初判是导出保真度问题，逐项排查后确认两侧计算其实等价：

| 假设 | 检验方式 | 结论 |
|---|---|---|
| 权重不同 | GGUF 张量 vs checkpoint 逐位比对，抽查 15 个张量 | `max|diff| = 0`，排除 |
| 精度不同 | PyTorch 侧 fp32 / bf16 / fp16 分别求 loss | 三者完全相同（7.3232），排除 |
| SWA 语义错位 | PyTorch 侧 SWA vs 全注意力求 loss | 仅差 0.02，而 llama.cpp 差 0.22，排除 |
| 误用滑动窗口 | llama.cpp verbose 日志 `n_swa` / `is_swa_any` | 均为 0，排除 |
| hparams 偏差 | 与官方 Qwen3-1.7B 逐项对比 | 完全一致；`rope type=2` / `rope scaling=linear` 是 qwen3 架构默认值，官方模型同样如此 |

**真正的根因**：`llama-perplexity` 的两个行为被误读了。

1. 当 `块数 × n_ctx < 序列长度` 时，llama.cpp **直接丢弃尾部 token**；
2. 它报的 `Final estimate: PPL` 取的是**最后一块**的困惑度，**不是全序列平均**。

也就是说，此前拿「llama.cpp 最后一块」去比「PyTorch 全序列平均」——
两个量根本不是同一个统计量。

**验证方法**：把序列按 llama.cpp 完全相同的粒度切块，逐块在 PyTorch 侧对齐计算。

| 块 | PyTorch nats | llama.cpp nats | 差 |
|---|---:|---:|---:|
| 块 1 | — | — | **−0.063** |
| 块 2 | — | — | **+0.143** |
| 块 3 | — | — | **−0.025** |

差异均值约 0，**无系统性偏移**，符合 bf16 数值噪声量级。结论：导出链路正确，
此前的 0.22 nats 是协议（measurement protocol）差异造成的伪信号。

**附带收益**：这一轮排查直接暴露了两个真实的工程坑，已回写导出器 ——
2D 权重矩阵必须写成真 F16（原先整体 F32，体积 453.8MB → 227.3MB），
以及补齐 `tokenizer.ggml.eot_token_id`。F16 转换后困惑度从
`[1486.73, 1606.24, 1472.78]` 变为 `[1488.01, 1607.27, 1473.46]`，差异 0.1%。

**残留告警**：`special_eos_id is not in special_eog_ids`。
`eot_token_id` 键已确认写入 KV，疑为 llama.cpp 内部 token 属性推断逻辑。
生成能正常停止、困惑度不受影响，归为无害告警。

**使用 llama.cpp 评测时的硬约束**（踩过的坑）：

- `llama-perplexity` 要求序列长度 ≥ `2 × n_ctx`，否则拒绝执行；
- 工具**打不开含中文的路径**，必须设 `cwd` 到纯 ASCII 目录并传 ASCII 相对文件名，
  模型路径走宽字符 API 可以。

## 七、工程踩坑记录

以下问题均会导致**静默错误**——不报错，但模型完全不可用。

### 1. RoPE 风格不匹配（最严重）

最初按 GPT-NeoX 的半旋转风格实现 RoPE。但 llama.cpp 的 `qwen2`/`qwen3` 架构
固定使用 **interleaved(NORM) 风格**（按偶/奇位切分旋转）。
不统一的话，PyTorch 里一切正常，导出 GGUF 后 llama.cpp 推理输出纯乱码。

**修复**：改为
```python
x_even, x_odd = x[..., 0::2], x[..., 1::2]
return torch.stack((x_even*cos - x_odd*sin, x_even*sin + x_odd*cos), -1).flatten(-2)
```

### 2. 全局注意力层因果性泄漏

原本所有层统一传 `attn_mask=swa_mask`，GA 层传 `None` 配合 `is_causal=False`，
结果 GA 层变成了**双向注意力**，未来 token 泄漏进当前预测。

随机初始化时 loss ≈ ln(16384) 完全看不出问题。

**修复**：`(attn_mask is None)` 时传 `is_causal=True`，同时走高效 kernel。
并写了因果性回归测试：改动位置 20 之后的输入，位置 0-19 的 logits 差异必须为 0。

### 3. HuggingFace 直连不通

`huggingface.co` 全部超时，`hf-mirror.com` 正常。但即使设了 `HF_ENDPOINT`，
部分 API（如 fineweb-edu 的 tree 列表）仍会直连并失败——该数据集最终弃用，改用英文维基。

### 4. PowerShell `Out-File` 缓冲

`python xxx.py | Out-File log.txt` 会长时间缓冲，长任务的实时进度完全看不到，
一度误判为"进程卡死"。改为脚本内自带日志文件直接 `write + flush`。

### 5. `tokenizers` 加载后 `model.merges` 为空

`Tokenizer.from_file(...).model.merges` 在本机 tokenizers 版本返回空列表，
导致导出的 GGUF 有 0 条 merges，tokenizer 形同虚设。
必须直接解析 `tokenizer.json` 的 `model.merges` 字段。

### 6. byte-level BPE 训练内存膨胀

ByteLevel 预分词会把中文拆成单字，喂给 BPE 训练器的词频表随输入量急剧膨胀。
20 万行中文吃掉 20GB 内存。修复：限制行长 1500 字符 + 样本量降到 8 万行
（对 16K 词表完全够用），内存降到 8.6GB。

### 7. MTP 损失形状错位

`mtp_labels` 在调用方已被切成 `x[:, 2:]`，函数内部又切了一次 `[:, :-1]`，
导致 cross_entropy 形状不匹配。改为内部按 depth 自动对齐：
`depth d` 预测 `labels[:, i+2+d]`。

### 8. SFT 对话模板的 int/list 拼接

`sep` 是 token id（int），却写成 `+ sep +` 与列表相加，抛
`TypeError: can only concatenate list (not "int") to list`。应为 `+ [sep] +`。

### 9. GGUF 预分词器写成 "default"

这是本项目最隐蔽的一个 bug。GGUF 的 `tokenizer.ggml.pre` 写成 `"default"` 时，
llama.cpp 的切分规则与训练时的 HF ByteLevel 不一致。表现是：**模型能加载、
能生成、不报任何错**，但生成的文本与训练分布不符。

只有用 `llama-tokenize` 对**长文本**逐 id 比对才能发现——短句（如 4 个汉字）
两边恰好一致，掩盖了问题。

### 10. llama.cpp 工具无法打开含中文的路径

这套 llama.cpp 是窄字符版，`llama-perplexity -f` / `llama-bench` 打不开
`F:\自研大模型\...` 下的文件（`No such file or directory`），但 `-m` 模型路径
走的是宽字符 API 所以能加载。

**绕开办法**：把工作目录设为目标文件夹，只传 ASCII 相对文件名。
（这也是当初 llama-bench 报 "failed to load model" 的真实原因，不是模型有问题。）

### 11. llama-cli 是交互式程序，会挂住等 stdin

生成完 n 个 token 后它会回到 `> ` 提示符等待输入。脚本里必须
`stdin=subprocess.DEVNULL`，否则进程永远不退出。

另外，本机环境下直接在前台调用 llama-cli 会导致调用方拿到空输出
（外部中断信号打断了 Python 的 `wait()`），需要用 `Start-Process` 独立启动、
把输出重定向到文件再读取。

## 八、局限与后续方向

### 当前的真实局限

1. **模型能力有限**。108M 参数 × 2 亿 token ≈ 1.85 token/param，
   而 MiMo-7B 是 25 万亿/70 亿 ≈ 3500 token/param。本模型只能学到
   中文/英文的统计规律和局部连贯性，不具备可用的问答能力。
2. **上下文仅 512**。MiMo 原生 32K 起步。
3. **MTP 未用于推理加速**。训练时提供了辅助信号，但投机解码草稿模型
   需要 llama.cpp 侧支持后才能兑现 2-3 倍吞吐。
4. **滑动窗口的推理路径待定**。MiMo-Lite 的 GA 层交错在第 5、11 层（非"前 N 层"式连续），
   而 llama.cpp 对 qwen3 的滑动窗口语义是"前 n_swa 层使用窗口"。
   导出时已写入 `qwen3.swa_nums` / `qwen3.ga_nums` 记录真实层号，
   但这些键是否被 llama.cpp 识别需要实测对比。

### 可做的扩展

1. **续训**：`--resume` 随时接着跑，语料还有 6.43 亿 token 未过完。
2. **换更大基座**：改 `MiMoLiteConfig` 即可，d_model/layer 均可调，tokenizer 无需重训。
3. **MTP 投机解码**：llama.cpp 若支持，可直接兑现吞吐提升。
4. **量化**：108M 的 F16 只有 454MB，Q8 量化后约 230MB，可与其他模型同卡共存。
5. **MOPD 简化实现**：`grpo.py` 的 teacher 框架已留出扩展点。
